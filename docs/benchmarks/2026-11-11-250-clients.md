# Benchmark: 250 clients, 4 messages per second per client

**Date:** 2026-11-11. **Implementation:** `Shisetsu-Code/Api-chat` (Rust/WASM, Cloudflare Workers, ChatRoom DO SQLite and UserHub DO WebSockets).  
**Environment:** GitHub Actions Ubuntu runner, Wrangler 4.160.0 running Cloudflare runtime locally via Miniflare/workerd, with synthetic D1 and DO data. **NOT a Cloudflare remote benchmark.**

## Workload

- 250 separately authenticated clients and 250 established WebSocket connections, distributed over 125 two-member rooms.
- Open-loop HTTP sends, each client sending 4 messages/second for 15 seconds (15,000 planned requests; 1,000 messages/second target).
- One distinct synthetic `CF-Connecting-IP` header per client (198.18.0.0/15 test network) to model distributed clients. These are not 250 real geographically separate users.
- AES-256-GCM encrypted storage and normal auth/session checks enabled; no authentication bypass.
- Timeout per request 25 seconds, at most 4,000 outstanding HTTP requests in the **load generator**. Excess scheduled requests are counted as dropped *before* reaching the API.
- Each run waits for pending HTTP requests, then for notification fanout, and uses paginated authorized HTTP sync to compare confirmed messages against persisted messages.
- Separate baseline: same topology with 1 message/second/client (250 messages/second target; 3,750 planned).

All observed HTTP responses to message requests were HTTP 200; the remaining launched requests timed out in the load generator. No HTTP 429 was observed in these runs with simulated distinct client addresses.

`Messages persisted and recovered` counts messages whose client request timed out as well as messages with ACKs, and **must not** be interpreted as the server's measured 15-second throughput. The server continued processing requests after the initial load window.

The 100% notification coverage reported in the benchmark applies **only to messages with received ACKs**. It does not prove delivery of all messages whose HTTP request timed out.

## Interpretation

**The requested 1,000 messages/s target was not achieved in this environment.** Even the 250 messages/s control suffered long ACK delays. This benchmark stresses both the single-host local Workers/D1 simulation and the Node.js request generator; it does not isolate production Cloudflare capacity.

**Durability and idempotency are essential.** Across runs, thousands of messages had been committed in SQLite even though their original client-side HTTP requests expired. A client must query by its idempotency key or retry with the same client ID, rather than generating a new message on timeout.

Likely contributors requiring a measured breakdown are D1 session checks on each HTTP send, per-message DO transaction/sync, fanout to two UserHub DOs, SQLite timing and the load generator's single-host capacity. No individual stage has been proven the bottleneck yet.

## Next validation

1. Deploy **isolated staging** to actual Cloudflare Workers, D1 and Durable Objects with live HTTPS (not public production) and instrument per-stage durations. Never use production credentials or user messages in a benchmark.
2. Run a distributed generator from multiple regions/hosts, with many actual network endpoints; report achieved offered rate and generator saturation separately.
3. Measure sustained load at 50, 100, 250, 500 and 1,000 messages/s for longer windows, with concurrency control and backoff.
4. Confirm server-side outbox age, fanout delivery latency and per-room sequencing under a sustained stream, including WebSocket disconnect/reconnect.
5. Verify Cloudflare rate limits: the current 600 requests/min/IP setting makes a single-IP 1,000 requests/s benchmark impossible without representative distributed clients or a controlled test-specific policy.
